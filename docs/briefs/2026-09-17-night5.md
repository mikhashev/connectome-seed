## 1. What night 5 is

Two runs, in this order. **The composition is recommended here, not yet decided by anyone** —
Mike still has to choose it (`docs/plans/2026-09-17-endpoint-before-n.md:216`, decision 3: "Whether
night 5 is the third replicate pair … or something else").

| position | label | seed | id | tag | iterations | rungs | determinism |
|---|---|---|---|---|---|---|---|
| 1st | `3‴` | 3 | `9992/903` | `rep` | 250,000 | 1000,5000,25000,250000 | off (`--no-determinism`) |
| 2nd | `0″` | 0 | `9992/000` | `night5` | 250,000 | 1000,5000,25000,250000 | off (`--no-determinism`) |

This is the same run configuration as nights 1–4: 250,000 iterations, the same four-rung ladder,
`--no-determinism` (`docs/experiments/004-night4-replicate-3prime-and-seed-5.md:33-34`, argv
identical across three nights on this point).

Ordering follows from `tools/night/launch_wave.py`'s own job-placement rule: a `--replicate-of`
job not matched by a same-seed `--seeds` job in the same invocation is placed **first**, before
any plain-seed job (`launch_wave.py:98-114`). `3‴` is a `--replicate-of 3` job with no `--seeds 3`
alongside it, so it goes first; `0″` is a plain `--seeds 0` job (tag `night5`, matching the wave's
own `--tag`), so it lands second, at the ordinary id `<ensemble>/000`
(`launch_wave.py:94-95`: `jobs.append({"seed": s, "id": f"{a.ensemble}/{s:03d}", "tag": a.tag})`).
`0″` is deliberately **not** launched via `--replicate-of 0` — that path hard-codes `tag="rep"`
(`launch_wave.py:108`) and would not give the `night5` tag this composition specifies.

## 2. The ensemble is 9992, not 9991 — a safety requirement, not a preference

`launch_wave.py:108` hard-codes a replicate's id: `rep = {"seed": s, "id": f"{a.ensemble}/9{s:02d}",
"tag": "rep"}`. Under ensemble 9991 this pattern gives `3‴` the id `9991/903` — already the network
directory of night 4's own replicate 3′ (`docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20`,
run `9991/903`). `0″`'s own path, the plain `--seeds 0` scheme (`launch_wave.py:95`,
`f"{a.ensemble}/{s:03d}"`), gives id `9991/000` under 9991 — already the network directory of night
1's original run 0 (`docs/experiments/001-run0-and-replicate.md:40`, run `9991/000`).

Either collision is caught, not silently overwritten: `run_individual.py:375-382` refuses to start
when `not a.resume and network_dir.exists()` — `"refused: network dir exists (datamate raises
FileExistsError on incompatible config; nothing deleted)"`, exit code 2. So launching this
composition under 9991 would not corrupt existing data, but it would not run at all; 9992 is the
ensemble that lets both jobs start.

**Comparability is unaffected by the ensemble number.** The individual a run trains is set by
`--seed` alone: `network.node_config.bias.seed=<seed>` is composed into the Hydra config
(`run_individual.py:356`) and asserted against the live network's own config immediately after
solver build — `rec["bias_seed_in_network_config"] = int(net.config.node_config.bias.seed);
assert rec["bias_seed_in_network_config"] == a.seed, (...)` (`run_individual.py:408-409`). `--id`
only sets the output coordinate: it is passed to flyvis as `ensemble_and_network_id=a.id`
(`run_individual.py:350`) and used to build the on-disk network directory,
`network_dir = results_dir / "flow" / a.id` (`run_individual.py:366`). Nothing in that path reads
back into training. `3‴` under `9992/903` and `0″` under `9992/000` are seed-3 and seed-0
individuals in exactly the sense nights 1–4's runs were, regardless of the ensemble digit.

## 3. Why these two runs — the pre-registered reading

**`3‴` gives a second twin difference at a fixed seed, entirely inside one boot session.** Seed 3
now has three runs in one session (night 3's original at `9991/003`, night 4's replicate 3′ at
`9991/903`, and `3‴` at `9992/903`), so for the first time the question "is the 3′−3 gap
(+10.4309, `docs/experiments/004-night4-replicate-3prime-and-seed-5.md:91`) — or, for that matter,
the 0′−0 gap (+12.7279, `docs/experiments/001-run0-and-replicate.md:68`) — a floor on run-to-run
spread, or a single observation" gets a direct answer from repeats of one seed, rather than an
inference across different seeds' twin gaps. **With three runs, the estimate of run-to-run spread
has 2 degrees of freedom and is a first estimate, not a good one** — the plan's own caveat on a
third replicate pair states this directly: "at three pairs the sd of σ_rep is still of order ±50 %"
(`docs/plans/2026-09-17-endpoint-before-n.md:103-104`, Ark, 2026-09-17).

**`0″` measures the seam between two boot sessions, not a third clean replicate of seed 0.** The
machine restarted once as a Windows-Update cycle, and the authoritative instant is the kernel's
own: **2026-09-14T23:31:21.500Z**, from `Microsoft-Windows-Kernel-General` event **id 12** — "The
operating system started at system time 2026-09-14T23:31:21.500000000Z" (read from the live System
log by CC, 2026-09-17; first found by Ark the same day). Two details that only the log carries:
the kernel logged **three** id-12 starts inside two minutes — `23:29:42.500Z`, `23:30:35.500Z`,
`23:31:21.500Z` — the signature of an update restart cycle, so **session B begins at the last of
them**; and night 2's first seed-2 attempt therefore died about **38 seconds** after its last
heartbeat (`results/night2/wave_night2.progress.log`, last line `2026-09-14T23:29:04Z ... iter
12700/250000`, then the first start at `23:29:42.500Z`), not the ~130 s an earlier reading of this
gave against a derived boot value. Re-run afterward as `night2b`
(`docs/next-session-plan.md:87-90`).

**The derived values in the repository read lower than the kernel's, and that is the drift, not a
second reboot.** `results/diagnostics/c3/machine_state.json:10` (and 21/32/43/54) records
`2026-09-14T23:31:17Z`; `docs/briefs/2026-09-17-machine-state-field.md:115` reconstructs the same
value; a WMI `LastBootUpTime` read on 2026-09-17 gives `23:31:14.911Z` and a `GetTickCount64`
reconstruction `23:31:14.618Z`. All name the same session; they sit 4.2 s and 6.6 s below the
kernel's 23:31:21.5 respectively, drifting further the later they are read. **The kernel's id-12
line is the value to cite; the derived ones are the value to print.** Both existing replicate pairs sit on opposite sides of it: run 0 and run 0′
(`9991/000`, `9991/900`) both finished inside **session A**, entirely before the reboot
(`docs/experiments/001-run0-and-replicate.md:40`: run 0 finished `2026-09-13T22:40:56Z`, run 0′
finished `2026-09-14T02:39:51Z` — both roughly a day before the restart);
seed 3 and replicate 3′ both ran inside **session B**, entirely after it
(`docs/experiments/003-night3-seeds-3-and-4.md:20`: seed 3 started `2026-09-15T20:35:26Z`;
`docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20`: 3′ started
`2026-09-16T20:27:30Z`). Pooling the two pairs' gaps into one estimate of run-to-run spread
therefore rests on an unstated assumption — that run-to-run variance is the same across sessions
A and B. `0″` is the only run that can turn that assumption into a number: it repeats seed 0
**inside session B**, so `0″ − (session-B seed-0 baseline)` is not available (session B never
recorded an original, un-rebooted seed-0 run to compare against) but `0″`'s own trajectory, read
against session A's `0`/`0′` pair, is the first cross-session observation this project has. **State
plainly: `0″` is not a clean replicate of seed 0 and must never be pooled with the (0, 0′) gap as
if it were a third observation of the same quantity** — it is a single observation of a different
thing, the session seam itself.

## 4. Acceptance

Each item is a gate that can fail; a failed gate voids the run or the pair it belongs to (§5).

1. **`uptime_s` strictly increases** between the `machine_state_start` and `machine_state_end`
   records of each run (`run_individual.py:699`, `:749`), and across the two runs in the wave (end
   of `3‴` < start of `0″`). A decrease means a reboot occurred mid-night; the affected run and, if
   it straddles the seam, the pair built on it, is void.
2. **`boot_time_utc` is printed, not gated.** It is computed as `time.time() − uptime_s`
   (`docs/briefs/2026-09-17-machine-state-field.md:74`), so it drifts with the wall clock —
   measured at roughly 3 s/day within one session: against the kernel's `23:31:21.500Z` the same
   boot reads `23:31:17Z` in `results/diagnostics/c3/machine_state.json` (2026-09-17 06:49Z) and
   `23:31:14.6–14.9Z` when read on 2026-09-17 20:38Z — monotonically lower the later it is taken.
   An equality gate on it would fail a correct implementation, and a fixed tolerance would too,
   since the error grows with elapsed uptime. Record it in each run's
   `machine_state_start`/`machine_state_end`; do not compare it for equality.
3. **An independent witness from the Windows event log**, recorded beside each run, because it does
   not depend on any of our own code: System log, Kernel-General event id 12 ("The operating system
   started") or EventLog event id 6013 (system uptime), queried for the night's own window. This is
   a new check, not yet exercised on any run in this repository — record whatever `wevtutil` or
   `Get-WinEvent` returns for that window next to the run, even if it is empty.
4. **`json_iter_wall_median_all_s` inside [0.0598, 0.0622].** This is the band of all eight existing
   runs' own `json_iter_wall_median_all_s` field (`wave_night1.json:53,92` = 0.061446, 0.060918;
   `wave_night2.json:53` = 0.062248; `wave_night2b.json:53` = 0.061134; `wave_night3.json:53,92` =
   0.061191, 0.059796; `wave_night4.json:53,92` = 0.060738, 0.060875) — min 0.059796, max 0.062248,
   spread (0.062248 − 0.059796) / 0.059796 = 4.10 %, across four calendar days and the one reboot in
   §3. Outside this band, the environment moved (another process on the GPU, thermal throttling, a
   different driver) and the pair is incomparable — this is visible before any statistics are run
   on the loss curves.
5. **The keys `machine_state_start` and `machine_state_end` must be present in both run jsons.**
   Their absence would mean the wrong `run_individual.py` was used — the machine-state patch is
   applied to the working copy (`docs/briefs/2026-09-17-machine-state-field.md`, "Applied
   2026-09-17"), but the recorded patch artefact itself does not carry every field it produces:
   `grep -c boot_time_utc docs/briefs/2026-09-17-run_individual-machine-state.patch` returns **0**,
   while the same search against the applied file, `tools/night/run_individual.py`, returns **3**
   (the field's definition and its use); the two call sites are at `run_individual.py:699` and
   `:749` exactly as `docs/briefs/2026-09-17-machine-state-field.md:79,84` records them. No run
   json committed before the patch carries these keys — `grep -c machine_state_start
   results/night4/night4_9991-005.slim.json` returns **0** (night 4 finished
   `2026-09-17T04:29:27Z`, `results/night4/wave_night4.json`, before the patch was applied at
   `08:19:01Z` the same day, `docs/briefs/2026-09-17-machine-state-field.md:66`). **Night 5 is this
   field's first real exercise on a live run**, not a re-check of something already seen working
   end to end.

## 5. Void conditions

- **The GPU is not free at launch.** Another resident process changes iteration timing, which is
  exactly what gate 4 (§4.4) would then (correctly) catch — but catching it after two four-hour runs
  is a wasted night; check `nvidia-smi` before launch.
- **A reboot during the night** — gate 1 (§4.1) catches this after the fact; if it happens between
  `3‴` and `0″`, `0″` gains a second session seam inside the wave itself and is void even if it
  otherwise completes, because it would then no longer be "one repeat of seed 0 inside session B."
- **Either run does not reach `final_iteration` 250,008** (the observed endpoint of `--n-iters
  250000` under this project's checkpoint cadence, matching all eight runs on record, e.g.
  `docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20-21`) — a partial run is void by
  this project's existing convention (`docs/next-session-plan.md:90-91`, night 2's
  `002_killed_by_reboot`: "an interrupted run is a failed run").
- **The wave is launched under ensemble 9991.** Per §2 this is either refused outright by
  `run_individual.py:375-382` (exit code 2, no training started) or, if the composition were
  changed to avoid that refusal, would silently target directories this repository already treats
  as night 1's and night 4's own records — never acceptable regardless of outcome.

## 7. Boundaries — what night 5 does and does not establish

- **It does not read the (b) test.** `docs/plans/2026-09-17-endpoint-before-n.md:204` — "(b) is
  read once, at the final N — but N is chosen after step 3, not before." Night 5 is not step 3.
- **It does not choose N.** N (8 or 10) is a registered choice made "after step 3"
  (`docs/plans/2026-09-17-endpoint-before-n.md:94-98`), and night 5 is not that step either.
- **It does not decide road A or road C.** Those follow from the reachability gate's outcome
  (`docs/plans/2026-09-17-endpoint-before-n.md:90-93`, step 3), which has not run yet.
- **By the plan's own order of work, night 5 comes after the reachability-endpoint gate, not
  before it.** §3 of `docs/plans/2026-09-17-endpoint-before-n.md` lists: (1) pre-register the
  endpoint, (2) read it (CPU only), (3) gate on it, (4) only then the N floor, (5) "if nights are
  bought, the first night is a third replicate pair" — this brief's own composition. Running night
  5 ahead of step 3 is a decision the owner has to take knowingly; this file does not make that
  case either way, and does not schedule itself (§0 banner, and this line).
- **Two runs give a first estimate of run-to-run spread, not a reliable one** — 2 degrees of
  freedom (§3); the ±50 % figure on σ_rep at three pairs (`docs/plans/2026-09-17-endpoint-before-n.md:103-104`)
  applies to whatever this night adds to it.
- **`0″`'s reading is a single observation of a difference between two boot sessions**, not a
  replicate of seed 0 in the sense (0, 0′) are replicates of each other (§3). No σ or rate is
  established by one such observation.
- **No number in this file is new.** Every figure above is read from a committed artefact at the
  cited path and line, or computed by simple arithmetic over such figures (the wall-time sum in
  §6, the band spread in §4.4); nothing here is measured for the first time by this brief.
- **A reachability-endpoint event-log witness (§4.3) has not been exercised on any run in this
  repository before night 5** — stated as a gap, not glossed over: this brief cannot cite a prior
  instance of it working, only the general Windows convention it relies on (Kernel-General event
  id 12 / EventLog event id 6013 for a system start), because no committed record in this
  repository has used it yet.
