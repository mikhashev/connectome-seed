## 0. Before you launch — run the pre-flight, do not recall it

```
powershell -ExecutionPolicy Bypass -File tools\night\preflight_night5.ps1
```

Exit 0 means every check passed; **exit 1 means the night must not start**; exit 2 means
something needs a human decision. Nothing in it starts anything.

**Why a pre-flight exists at all, and why this one is not bureaucracy.** Every gate in §4
fires *after* the night: gate 7 needs a run json, gate 8 compares environments, and gate 4
catches GPU contention only once two four-hour runs have already been spent. The confounder
that has actually recurred is caught by none of them in advance — another process resident
on the card. It was stopped on 2026-09-17 and was **back on 2026-09-18 under a new PID**,
holding 27.8 GiB of the 32.6 GiB card. A recurring confounder is answered by a check that
runs every time, not by a sentence someone is meant to remember.

What it refuses on, each with the measured value printed beside the expected one:

| check | the rule, and where it comes from |
|---|---|
| **GPU free** | nights 1–4 each ended with **3,720–4,805 MiB** in use — that is the whole card, desktop included — so anything above 6,000 MiB before the start means something else is resident and gate 4's timing bands, measured on a free card, do not apply |
| **compute processes** | any resident `llama`/`python`/`vllm`/`ollama`/`torch` process is named and refused |
| **`9992/000` and `9992/003` absent** | `run_individual.py:375` refuses per run with exit 2 and "nothing deleted"; a collision on the **second** job kills only that job, four hours in |
| **venv answers** | `python 3.10.20`, `torch 2.9.1+cu128`, `cuda_available True`, `flyvis 1.2.0` |
| **reboot pending** | a queued Windows restart will land inside the night |
| **the command itself** | dry-run now, and the order checked: seed 0 at `9992/000` **first** |

And two it warns on rather than refuses, because they are decisions and not facts:

- **Active hours.** Windows defers an update restart **only inside** active hours. They are
  currently **08:00–17:00 local**, which leaves the entire night unprotected — and that is
  precisely the state in which the restart of **2026-09-14 23:31 UTC** killed a run that is
  not in the substrate at all. Windows allows an 18-hour span, so **17:00–08:00** would
  cover the night. This is a setting, not a gate, and it is the single cheapest thing that

- **A dirty or unpushed tree**, because the night's provenance then names one.

**Both runs are launched as plain seeds, and the ordering is the order of the seed list**
(`-Seeds "0,3"`). Verified by dry run rather than read off the code: with `-Seeds "0,3"` the
launcher emits seed 0 at `9992/000` first and seed 3 at `9992/003` second, and with `-Seeds "3,0"`
it emits them the other way round, so the list order is the run order
(`launch_wave.py:94-95`: `jobs.append({"seed": s, "id": f"{a.ensemble}/{s:03d}", "tag": a.tag})`).

**`0″` goes first, and the order carries an argument (corrected 2026-09-18).** A night can fail to
reach its second run — the historical reboot landed near 23:30 — so the first position belongs to
whichever run can disqualify the most if it is the only one that finishes. That is `0″`: seed 0's
twin gap is **12.1749**, against a spread of **12.1922** over all six individuals in the same
field (§7), so the twin difference is very nearly the entire between-individual spread, and every
reading in this project is bounded by it. A third run of seed 0 tests whether that 12.17 is typical
of seed 0 or was one unlucky pair; if it is typical, the ranking-class endpoint is dead on this
substrate regardless of what any other run says. Seed 3's twin gap is 7.6059 and binds nothing on
its own; `3‴` sharpens the C3 picture and is the second-most valuable run, not the first.

**Why this needed correcting at all, recorded because the mechanism is more interesting than the
fix.** v1 put `3‴` first for a purely mechanical reason: `launch_wave.py:98-114` places an
unmatched `--replicate-of` job ahead of any plain-seed job, and under v1's launch form `3‴` was
that job. When v2 made both runs plain seeds the reason disappeared, the order was kept out of
inertia, and a scientific-sounding justification was written underneath it — an argument
constructed to fit an arrangement that had arisen for an unrelated reason. The ordering argument
above predates the brief; it was stated in the group chat before v2 was written and then not
carried into the file, which is the same "the edit list was rewritten from scratch instead of
derived" failure as the three lost review points of 2026-09-17.

**Rule, recorded because it cost a decision (2026-09-18).** Neither run is launched through
`--replicate-of`, although `3‴` is in every scientific sense a repeat of seed 3. That path
hard-codes two things at `launch_wave.py:108` — `tag="rep"` and the id `<ensemble>/9<seed:02d>` —
and both are wrong here. The tag would split one wave across two file prefixes (`rep_*` and
`night5_*`), and the id `9992/903` would announce "replicate" about a **third** run, which the
`9xx` convention cannot express: it distinguishes *a* replicate from an original and has no way to
say *which* repeat. Under the plain form the id `9992/003` says what is true and nothing more — the
seed-3 run of ensemble 9992 — at the price of losing the `9xx` marking for a run that is a repeat.
**That price is paid deliberately: a name that cannot express the distinction it is being used for
is the defect this repository has already been bitten by twice** (commits `2334f32` and `31febd8`,
both about a directory name that lied). The replicate marking is carried by the label `3‴` in this
brief and by the experiment record, not by the id.

**One tag, one prefix.** Both runs carry tag `night5`, so the per-run files this wave writes are
`night5_9992-003.*` and `night5_9992-000.*`. This is the second reason the plain form was chosen:
under the `--replicate-of` form the wave would have written `rep_9992-903.*` and
`night5_9992-000.*`, and any collector keyed on one tag would have picked up exactly one of the two
runs — the same class of defect as the `9991/*` glob caveat, one level in. A collector keyed on
`night5` now sees both, and one keyed on the ensemble sees both.

## 2. The ensemble is 9992, not 9991 — a safety requirement, not a preference

Both jobs take their id from the plain-seed scheme, `f"{a.ensemble}/{s:03d}"`
(`launch_wave.py:94-95`), so under ensemble 9991 they would land on `9991/003` and `9991/000` —
**both already occupied**: `9991/003` is night 3's own run of seed 3
(`docs/experiments/003-night3-seeds-3-and-4.md`) and `9991/000` is night 1's original run 0
(`docs/experiments/001-run0-and-replicate.md:40`). Neither is a near miss; each is the exact
directory of a finished run on record.

The rejected `--replicate-of` form collides too, one directory over: it hard-codes
`rep = {"seed": s, "id": f"{a.ensemble}/9{s:02d}", "tag": "rep"}` (`launch_wave.py:108`), which
under 9991 gives `3‴` the id `9991/903` — night 4's replicate 3′
(`docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20`). So the ensemble digit, not the
launch form, is what keeps this composition off existing data; §1's choice of form was made for
naming and collectors, and changes nothing here.

Either collision is caught, not silently overwritten: `run_individual.py:375-382` refuses to start
when `not a.resume and network_dir.exists()` — `"refused: network dir exists (datamate raises
FileExistsError on incompatible config; nothing deleted)"`, exit code 2. So launching this
composition under 9991 would not corrupt existing data, but it would not run at all; 9992 is the
ensemble that lets both jobs start.

**Comparability is unaffected by the ensemble number.** The individual a run trains is set by
`--seed` alone: `network.node_config.bias.seed=<seed>` is composed into the Hydra config
(`run_individual.py:356`) and asserted against the live network's own config immediately after
solver build — `rec["bias_seed_in_network_config"] = int(net.config.node_config.bias.seed);
assert rec["bias_seed_in_network_config"] == a.seed, (...)` (`run_individual.py:408-409`). `--id`
only sets the output coordinate: it is passed to flyvis as `ensemble_and_network_id=a.id`
(`run_individual.py:350`) and used to build the on-disk network directory,
`network_dir = results_dir / "flow" / a.id` (`run_individual.py:366`). Nothing in that path reads
back into training. `3‴` under `9992/003` and `0″` under `9992/000` are seed-3 and seed-0
individuals in exactly the sense nights 1–4's runs were, regardless of the ensemble digit.

## 3. Why these two runs — the pre-registered reading

**`3‴` gives a second twin difference at a fixed seed, entirely inside one boot session.** Seed 3
now has three runs in one session (night 3's original at `9991/003`, night 4's replicate 3′ at
`9991/903`, and `3‴` at `9992/003`), so for the first time the question "is the 3′−3 gap
(+10.4309, `docs/experiments/004-night4-replicate-3prime-and-seed-5.md:91`) — or, for that matter,
the 0′−0 gap (+12.7279, `docs/experiments/001-run0-and-replicate.md:68`) — a floor on run-to-run
spread, or a single observation" gets a direct answer from repeats of one seed, rather than an
inference across different seeds' twin gaps. **With three runs, the estimate of run-to-run spread
has 2 degrees of freedom and is a first estimate, not a good one** — the plan's own caveat on a
third replicate pair states this directly: "at three pairs the sd of σ_rep is still of order ±50 %"
(`docs/plans/2026-09-17-endpoint-before-n.md:103-104`, Ark, 2026-09-17).

**The estimator, named before the reading (Ark, 2026-09-17).** Three runs of one seed give
**three** pairwise differences but only **two** degrees of freedom, and the three pairwise
differences are dependent (each pair shares one of the three runs) — averaging the three absolute
differences and calling the result σ_rep would repeat the very error class this session spent the
evening correcting. Registered instead: the ordinary unbiased (n−1) estimate of σ_rep, with its χ²
interval, which needs no normal-difference constant. The cost of that honesty: at three runs the
95 % interval for σ_rep is about [0.58·σ̂, 6.29·σ̂] — a factor of **10.9** wide; at four runs,
[0.57·σ̂, 2.92·σ̂] — a factor of 5.2. **So the third run disqualifies rather than estimates**, and an
estimate begins with the fourth run.

**`0″` measures the seam between two boot sessions, not a third clean replicate of seed 0.** The
machine restarted once as a Windows-Update cycle, and the authoritative instant is the kernel's
own: **2026-09-14T23:31:21.500Z**, from `Microsoft-Windows-Kernel-General` event **id 12** — "The
operating system started at system time 2026-09-14T23:31:21.500000000Z" (read from the live System
log by CC, 2026-09-17; first found by Ark the same day). Two details that only the log carries:
the kernel logged **three** id-12 starts inside two minutes — `23:29:42.500Z`, `23:30:35.500Z`,
`23:31:21.500Z` — the signature of an update restart cycle, so **session B begins at the last of
them**; and night 2's first seed-2 attempt therefore died about **38 seconds** after its last
heartbeat (`results/night2/wave_night2.progress.log`, last line `2026-09-14T23:29:04Z ... iter
12700/250000`, then the first start at `23:29:42.500Z`), not the ~130 s an earlier reading of this
gave against a derived boot value. Re-run afterward as `night2b`
(`docs/next-session-plan.md:87-90`).

**The derived values in the repository read lower than the kernel's, and that is the drift, not a
second reboot.** `results/diagnostics/c3/machine_state.json:10` (and 21/32/43/54) records
`2026-09-14T23:31:17Z`; `docs/briefs/2026-09-17-machine-state-field.md:115` reconstructs the same
value; a WMI `LastBootUpTime` read on 2026-09-17 gives `23:31:14.911Z` and a `GetTickCount64`
reconstruction `23:31:14.618Z`. All name the same session; they sit 4.2 s and 6.6 s below the
kernel's 23:31:21.5 respectively, drifting further the later they are read. **The kernel's id-12
line is the value to cite; the derived ones are the value to print.** Both existing replicate pairs sit on opposite sides of it: run 0 and run 0′
(`9991/000`, `9991/900`) both finished inside **session A**, entirely before the reboot
(`docs/experiments/001-run0-and-replicate.md:40`: run 0 finished `2026-09-13T22:40:56Z`, run 0′
finished `2026-09-14T02:39:51Z` — both roughly a day before the restart);
seed 3 and replicate 3′ both ran inside **session B**, entirely after it
(`docs/experiments/003-night3-seeds-3-and-4.md:20`: seed 3 started `2026-09-15T20:35:26Z`;
`docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20`: 3′ started
`2026-09-16T20:27:30Z`). Pooling the two pairs' gaps into one estimate of run-to-run spread
therefore rests on an unstated assumption — that run-to-run variance is the same across sessions
A and B. `0″` is the only run that can turn that assumption into a number: it repeats seed 0
**inside session B**, so `0″ − (session-B seed-0 baseline)` is not available (session B never
recorded an original, un-rebooted seed-0 run to compare against) but `0″`'s own trajectory, read
against session A's `0`/`0′` pair, is the first cross-session observation this project has. **State
plainly: `0″` is not a clean replicate of seed 0 and must never be pooled with the (0, 0′) gap as
if it were a third observation of the same quantity** — it is a single observation of a different
thing, the session seam itself.

## 4. Acceptance

Each item is a gate that can fail; a failed gate voids the run or the pair it belongs to (§5).

1. **`uptime_s` strictly increases** between the `machine_state_start` and `machine_state_end`
   records of each run (`run_individual.py:699`, `:749`), and across the two runs in the wave (end
   of `0″` < start of `3‴`). A decrease means a reboot occurred mid-night; the affected run and, if
   it straddles the seam, the pair built on it, is void.
2. **`boot_time_utc` is printed, not gated.** It is computed as `time.time() − uptime_s`
   (`docs/briefs/2026-09-17-machine-state-field.md:74`), so it drifts with the wall clock —
   measured at roughly 3 s/day within one session: against the kernel's `23:31:21.500Z` the same
   boot reads `23:31:17Z` in `results/diagnostics/c3/machine_state.json` (2026-09-17 06:49Z) and
   `23:31:14.6–14.9Z` when read on 2026-09-17 20:38Z — monotonically lower the later it is taken.
   An equality gate on it would fail a correct implementation, and a fixed tolerance would too,
   since the error grows with elapsed uptime. Record it in each run's
   `machine_state_start`/`machine_state_end`; do not compare it for equality.
3. **An independent witness from the Windows event log**, recorded beside each run, because it does
   not depend on any of our own code: System log, Kernel-General event id 12 ("The operating system
   started") or EventLog event id 6013 (system uptime), queried for the night's own window. Also
   query **Kernel-Power event ids 42 (sleep) and 107 (resume)**: `uptime_s`, read from
   `GetTickCount64` (§4.1/§4.2), does not reset on a suspend/resume cycle, so a sleep-and-resume
   would pass gate 1 unnoticed while changing the machine's state the way a reboot does — the
   Kernel-Power pair is the only witness in this gate that would catch it. This is a new check, not
   yet exercised on any run in this repository — record whatever `wevtutil` or `Get-WinEvent`
   returns for that window next to the run, even if it is empty.
4. **Four sub-gates on `s/iter` replace the single `json_iter_wall_median_all_s` band.**
   `json_iter_wall_median_all_s` (`run_individual.py:733`, `statistics.median(it)` over the
   unsliced `it = rec["iter_wall_s"]` array appended at `run_individual.py:663`) is a median over
   **every** iteration of the whole run — a mixture of the two cost regimes named in
   `docs/preregistration-reachability-endpoint.md` §10 (Ark's point) — so its 4.10 % spread is the
   mixture ratio wobbling, not the machine, and a contention window confined to one phase is
   absorbed by it rather than surfaced. Replaced with four sub-gates, all measured on the eight
   runs on record, from the `s/iter` column of `results/night*/wave_*.progress.log` (a rolling mean
   of the last 100 iteration times, `run_individual.py:679-680`):
   - **(4a) plateau level**, median of `s/iter` over iterations **5,000–150,000**: observed per-run
     0.0641–0.0652 (spread 1.7 %) → band **[0.0625, 0.0670]**.
   - **(4b) late level**, median over iterations **150,100–250,008**: observed 0.0457–0.0481 → band
     **[0.0445, 0.0495]**. State honestly that the ceiling is set by run `9991/004` at 0.0481, which
     is uniformly about 4.8 % slower than the other seven throughout its late phase — not a gap and
     not a burst (its maximum iteration gap is 100, identical to every other run) — and that the
     reason is unknown.
   - **(4c) ratio**, plateau/late: observed 1.33–1.41 → band **[1.30, 1.45]**.
   - **(4d) the transition iteration must be 150,000** (first logged sample 150,100). It was
     identical in eight of eight runs, including the one torn apart by the reboot (§3), which is
     what makes it a property of the schedule rather than of the environment. A different
     transition iteration means the configuration changed, not the machine.

   **The first 5,000 iterations are printed, not gated.** They are elevated and variable: per-run
   median over iterations ≤5,000 runs 0.0640–0.0672 against 0.0641–0.0652 on the plateau, and run
   `9991/903` reaches 0.0672 there — above gate 4a's own ceiling. The repository's existing field
   `iter_wall_median_1000_2000_s` is **not** a usable plateau statistic for the same reason: across
   the eight runs it spans 0.062767–0.067081, a 6.87 % spread, because iterations 1000–2000 are
   still inside the elevated region. And `iter_wall_median_after_first_epoch_s` is redundant — it
   equals `iter_wall_median_all_s` to within 1e-6 on every run, because one epoch is a small
   fraction of the run.

   All of these numbers were measured by CC on 2026-09-17 by a full scan of all nine job records in
   the progress logs, not by sampling.

6. **`results/night5/` is assembled in the same commit as the night's record, via an

7. **Night 5's resolved training config matches, line for line, the part of the config that is
   invariant across the eight runs on record — and that invariant part is *derived from those
   runs*, not listed by hand.** Each run stores its own fully resolved Hydra config, so the check
   is a comparison and not an argument:

   ```
   python tools/night/config_invariants.py --gate results/night5/<run>.slim.json \
       --against results/night1/*.slim.json results/night2/*.slim.json \
       results/night3/*.slim.json results/night4/*.slim.json
   ```

   **The first form of this gate was wrong, and the way it was wrong is the point (Ark,
   2026-09-18).** It read "differs in the seed and the id and nothing else" — a list written from
   memory of what ought to vary. Measured over the eight runs, `resolved_config_yaml` is **166
   lines, of which 162 are invariant and 4 vary**, and the four are
   `ensemble_and_network_id` (line 1), `network_name` (6), **`description`** (7) and `seed` (66).
   The third is the wave tag, and night 5's tag is `night5`, which matches no previous run — so the
   handwritten gate would have fired on the tag and the explanation would have arrived *after* the
   firing. The tool derives the varying set from the reference runs instead, refuses to compare at
   all if the configs differ in line count (a positional comparison of differently-shaped configs
   would silently compare unrelated keys), prints the new run's varying lines for the record, and
   **exits 3** when any invariant line differs.

   Both branches were watched to fire before the gate was relied on. Gating a real run against the
   other seven reports all 162 invariant lines matching and prints its four varying lines. A
   synthetic run with one invariant line altered — `stop_iter: 150000` → `200000`, exactly the
   drift that would void comparability while every timing gate passed — is caught at line 141 and
   exits 3.

   Two facts the derivation settled in passing, both of which support §3 rather than this gate.
   `activity_baseline: 5.0`, `activity_penalty: 0.1`, `stop_iter: 150000`,
   `below_baseline_penalty_weight: 1.0`, `above_baseline_penalty_weight: 0.1`, `n_iters: 250000`
   and `extent: 15` are **invariant across all eight runs**, so the 150,000 regime break stands in
   every run's own resolved config and this gate guards it. And there are exactly **two** `seed`
   lines: the varying one at line 66 sits inside the `node_config.bias` block — four lines above
   `penalize: {activity: true}` — while the invariant `seed: 0` at line 129 sits beside `n_folds`,
   `fold` and `original_split` and is the **data-split** seed, identical in all eight runs. The
   claim that one seed distinguishes our individuals and that the penalised parameter is the one it
   moves is therefore readable in our own committed run records, without opening the installed
   package at all.

   Ark predicted this gate would fire on the environment move and the changed `--out-dir`. It does
   not: **no invariant line contains an absolute path, `Temp`, `dir` or `home`** — there are no
   paths in `resolved_config_yaml` at all — so the gate is insensitive to both, and he withdrew the
   objection.
8. **The training environment is the same one that produced nights 1–4, by content and not by
   provenance.** The venv was copied out of an ended session's scratchpad on 2026-09-18 (§1), and a
   copy is an assumption until it is hashed. The check is a committed tool, not a description:

   ```
   python tools/venv_manifest.py <scratchpad>/.venv tools/.venv --out results/night5/venv_manifest.json
   ```

   It takes a per-file sha256 of both trees with `__pycache__` excluded (regenerated on import, so
   it differs legitimately and a digest including it would teach the reader to ignore a real
   difference), reduces each to a combined digest over the sorted (path, hash) pairs, names every
   file that differs or exists on one side only, and **exits 3 when they disagree** so that a
   caller cannot miss it. The manifest is recorded with the night, so a later question about which
   environment trained night 5 has an answer that does not depend on a temp directory that no
   longer exists. If the digests disagree, night 5's curves are not comparable to nights 1–4's and
   the pair is void.

   All three of its branches were watched to fire before it was relied on: a tree against itself
   reports `IDENTICAL` and exits 0; two different trees report the files present on one side only
   and exit 3; and two trees holding same-named files with different bytes report
   `present in both but differing : 1`, name the file, and exit 3. **On the real trees it reports
   identical** — 21,650 files each, combined sha256
   `94f7f483e8410e54887c98b20d520872823f1ba5ad9fa1c12d6b95359da7e318` on both sides. A check that
   has not been seen to fail on a case built to trip it is not enforced, only written down.

   **What gate 8 does not claim (Ark, 2026-09-18).** It asserts **identity, not workability**. The
   `Scripts\*.exe` console entry points in the copy are broken — `flyvis.exe` carries the old
   scratchpad interpreter path — but they are broken *identically* on both sides, so the manifest
   reports identical and is right to. Workability is established by the run itself and by the dry
   run of §1, never by this gate. **And the repository copy is now the canonical environment**: the
   scratchpad copy is to be treated as unused from night 5 onward, so that the question "which env
   is the real one" cannot arise again the way it did for `results/` — a second copy left
   unlabelled becomes a second source of truth within a month.

9. **The night's own arithmetic, named before the night (Ark, 2026-09-18).** What night 5 adds
   is a small design and not one number, and the estimator has to be named now because this is the
   last point at which naming it is free.

   | what | pairs | against what |
   |---|---|---|
   | within session A | 1: `0′ − 0` = **12.1749**, already measured | — |
   | within session B | 3, mutually dependent: `3′ − 3` = **7.6059** already measured, plus `3‴ − 3` and `3‴ − 3′` | each other |
   | across the A→B seam | 2: `0″ − 0` and `0″ − 0′` | the measured within-A twin gap, 12.1749 |

   Two consequences. First, `0″` yields **two** cross-seam differences and not one, because both
   `0` and `0′` sit in session A; they share a term, so they are not two independent draws and must
   not be averaged as though they were. Second, the comparison is against a **measured** quantity —
   the within-session twin gap on the same curves — and not against a threshold, which is what
   makes it a comparison rather than a test with an invented bar. The three within-B pairs are
   likewise dependent: three differences among three runs carry two degrees of freedom, not three.
   **Pre-registered here:** the night's estimator is the pair table above, reported as pairs with
   their dependence stated, and no pooled standard deviation is computed over `{0, 0′, 0″}` or
   `{3, 3′, 3‴}` as if the members were independent individuals — they are one individual each.

10. **What the night actually buys, in degrees of freedom rather than in pairs (Ark,
   2026-09-18 — checked here before the GPU is spent, not after).** It is tempting to say
   night 5 gives "a third twin difference". It does not give a third *independent* one.

   | individual | runs now | after night 5 | df on that individual |
   |---|---|---|---|
   | seed 0 | 2 (`0`, `0′`) | **3** (`0`, `0′`, `0″`) | 1 → **2** |
   | seed 3 | 2 (`3`, `3′`) | **3** (`3`, `3′`, `3‴`) | 1 → **2** |

   Three runs of one individual give **three pairwise differences carrying two degrees of
   freedom**, and they are mutually dependent — the third is determined by the other two.
   Pooled across the two individuals the night takes the replicate variance from **2 df to
   4 df**. The number of *independent individuals with replicates* stays **two**, and no
   two-run night can raise it.

   What that is worth, computed rather than asserted: the 95 % χ² interval for σ has a
   width ratio (upper/lower) of **12.07 at 2 df, 6.58 at 3 df and 4.80 at 4 df**, from
   `sqrt(chi2.ppf(0.975, ν) / chi2.ppf(0.025, ν))`. (Ark first had ×10.9 and ×5.2 and
   withdrew them against this computation, having spliced two rows of a table — his error
   ran *against* his own position, understating what the night buys.)

   **But 4 df is not a property of the night. It is a property of a definition that has not
   been chosen (Ark, 2026-09-18), and the correction matters because the two choices give
   different verdicts.** By session composition: seed 3's three runs (`3`, `3′`, `3‴`) all
   sit in boot session B, giving a clean 2 df; seed 0's do not — `0` and `0′` are in session
   A and `0″` in B, so seed 0 has exactly **one** within-session difference and two
   cross-session ones.

   | definition of replicate noise | `0″` in the twin side? | pooled df | σ interval | what between-gap must then be |
   |---|---|---|---|---|
   | (i) all run-to-run variation, session included | yes | **4** | 4.80 | stays as it is — already a mixture, 8 of its 15 pairs cross the seam |
   | (ii) within-session only | no, it becomes a separate printed measurement | **3** | 6.58 | must drop the 8 cross-seam pairs and stand on 7 |

   Under (ii) the night buys **a third less** than "2 → 4" suggests, and the seam leaves the
   criterion entirely. The curves do not exist yet, so this is the last moment at which the
   definition can be chosen freely; a day from now any choice reads as fitted to what is
   already visible. **It belongs in v2, written while the night runs.** It does not change
   the night: `{3‴, 0″}` is needed under either definition — `3‴` gives 2 df inside B,
   `0″` measures the seam.

   **And one condition neither of us stated, measured on 2026-09-18 (CC): all of the above
   assumes the machine does not reboot.** The kernel's own log shows the last boot at
   **2026-09-14T23:31:21Z** and nothing since — uptime 3 days 19 hours — so session B is
   still the live session and `3‴` will land in it. If a restart intervenes before the night
   ends, `3‴` and `0″` fall into a third session, seed 3 loses its clean 2 df, and under
   definition (ii) the pooled figure drops from 3 df to **2** — the night would buy nothing
   at all on the within-session side. A restart *between* the two runs splits them the same
   way, since they run sequentially over about eight hours. This is what turns the active-
   hours setting from an availability nuisance into a term in what the night is worth: at
   **08:00–17:00 local** restarts are deferred only during the day, and the machine's
   timezone is **UTC+7 (Tomsk)**, measured — so the 2026-09-14 restart at 23:31 UTC fell at
   **06:31 local**, outside the protected window, in exactly the hours the night occupies.

   **The consequence, and it is the reason this is written before the launch:** any v2
   protocol must state its requirement in **df and in independent individuals**, not in a
   count of differences. A v2 that says "≥3 twin differences" would be satisfied by three
   dependent ones. A v2 that needs three independent individuals with replicates is not
   satisfied by this night at all — and that is a ten-minute discovery now against an
   eight-GPU-hour discovery tomorrow.

## 5. Void conditions

- **The GPU is not free at launch.** Another resident process changes iteration timing, which is
  exactly what gate 4 (§4.4) would then (correctly) catch — but catching it after two four-hour runs
  is a wasted night; check `nvidia-smi` before launch.
- **A reboot during the night** — gate 1 (§4.1) catches this after the fact; if it happens between
  `3‴` and `0″`, `0″` gains a second session seam inside the wave itself and is void even if it
  otherwise completes, because it would then no longer be "one repeat of seed 0 inside session B."
- **Either run does not reach `final_iteration` 250,008** (the observed endpoint of `--n-iters
  250000` under this project's checkpoint cadence, matching all eight runs on record, e.g.
  `docs/experiments/004-night4-replicate-3prime-and-seed-5.md:20-21`) — a partial run is void by
  this project's existing convention (`docs/next-session-plan.md:90-91`, night 2's
  `002_killed_by_reboot`: "an interrupted run is a failed run").
- **The wave is launched under ensemble 9991.** Per §2 this is either refused outright by
  `run_individual.py:375-382` (exit code 2, no training started) or, if the composition were
  changed to avoid that refusal, would silently target directories this repository already treats
  as night 1's and night 4's own records — never acceptable regardless of outcome.

  (`docs/plans/2026-09-17-endpoint-before-n.md:90-93`, step 3), which has not run yet.
- **By the plan's own order of work, night 5 comes after the reachability-endpoint gate, not
  before it.** §3 of `docs/plans/2026-09-17-endpoint-before-n.md` lists: (1) pre-register the
  endpoint, (2) read it (CPU only), (3) gate on it, (4) only then the N floor, (5) "if nights are
  bought, the first night is a third replicate pair" — this brief's own composition. Running night
  5 ahead of step 3 is a decision the owner has to take knowingly; this file does not make that
  case either way, and does not schedule itself (§0 banner, and this line).

  freedom (§3); the ±50 % figure on σ_rep at three pairs (`docs/plans/2026-09-17-endpoint-before-n.md:103-104`)
  applies to whatever this night adds to it.
- **`0″`'s reading is a single observation of a difference between two boot sessions**, not a
  replicate of seed 0 in the sense (0, 0′) are replicates of each other (§3). No σ or rate is
  established by one such observation. **The reading is a multiplier, not "inside the spread"**
  (Ark's correction of CC's formulation, 2026-09-17): if `0″ − 0` is at least
  **2 × max(12.7279, 10.4309)** the session seam is significant; below that, the conclusion is only
  that the seam is not larger than the order of magnitude already called run-to-run noise. The
  reference itself rests on two pairs, so "inside the known spread" is not a decidable comparison —
  a multiplier against the larger of the two known gaps is.
- **No number in this file is new.** Every figure above is read from a committed artefact at the
  cited path and line, or computed by simple arithmetic over such figures (the wall-time sum in
  §6, the band spread in §4.4); nothing here is measured for the first time by this brief.
- **A reachability-endpoint event-log witness (§4.3) has not been exercised on any run in this
  repository before night 5** — stated as a gap, not glossed over: this brief cannot cite a prior
  instance of it working, only the general Windows convention it relies on (Kernel-General event
  id 12 / EventLog event id 6013 for a system start), because no committed record in this
